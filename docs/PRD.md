## 1. 背景与问题定义

### 1.1 家庭网络正在变成"小型数据中心"

过去五年，家庭网络的角色发生了根本变化。NAS 从"网络硬盘"变成了跑着 Docker、套件中心、相册服务、笔记服务的小型服务器；智能家居中枢、监控录像机（NVR）、软路由、Home Assistant 都在家庭内网提供 HTTP 服务。与此同时，IPv6 在国内三大运营商的普及率已超过 90%，大量家庭宽带获得了公网 IPv6 地址段——这意味着**内网服务第一次真正具备了被公网直接访问的条件**。

便利与风险是同时到来的。家庭服务一旦暴露，面对的不是"可能有人来攻击"，而是**确定会来的自动化扫描**：Shodan、Censys 以及大量僵尸网络每天在全网段扫描开放端口，从扫描到尝试弱口令、到利用已知漏洞，通常以小时计。近年来多起 NAS 勒索事件中，受害者的共同特征都是"把管理端口直接映射到了公网"。

### 1.2 现有方案在家庭场景下的失效点

家庭用户想保护自建服务，目前只有四类选择，每一类都有明显缺陷：

**第一类：直接端口映射 + 改密码。** 零成本，但等于把服务指纹、版本号、登录页全部暴露。一旦出现未修补的漏洞（NAS 厂商的补丁周期常常以月计），没有任何缓冲层。

**第二类：Nginx / Caddy 反向代理。** 能隐藏后端、统一 TLS，但它们不是 WAF。Nginx 开源版没有攻击检测能力；Caddy 的自动 HTTPS 很好用，但安全能力止步于"加几个响应头"。用户仍然需要自己拼装 fail2ban、crowdsec、地理封禁，配置分散且容易出错。

**第三类：企业级开源 WAF（ModSecurity + OWASP CRS、BunkerWeb、雷池 SafeLine）。** 能力足够，但设计假设是"有专职运维的企业"：
- ModSecurity + CRS 的配置是 SecLang 领域语言，700+ 条规则、五级偏执模式（Paranoia Level）、大量需要按业务调优的例外，家庭用户几乎不可能调对。默认配置下误报会直接打断正常使用（例如家庭相册的图片上传、笔记应用里的 Markdown 富文本）。
- BunkerWeb 功能全面，但底层是 NGINX + 多容器（实例 + Scheduler + 数据库），在 2GB 内存的 ARM NAS 上属于"为了防护先吃掉一半资源"。
- 雷池（SafeLine）体验最好，但官方部署形态是 Docker Compose 多容器，最低资源要求对低功耗设备不友好；其检测引擎闭源，规则不可审计，对"我想知道它为什么拦了我"的极客用户不透明。

**第四类：Cloudflare 等云 WAF。** 免费额度够用，但要求域名托管在第三方、流量全部经过第三方解密，家庭 NAS 的大文件传输、内网直连、隐私诉求都无法满足；且国内访问质量不稳定。

### 1.3 市场空白

把上面四类放在一起看，空白点非常清晰：

> **没有一个产品同时做到：纯 Rust 单二进制、ARM 低功耗可跑、默认安全且低误报、规则可审计可解释、面向家庭多域名多服务场景、并且把"性能不可预测时如何优雅降级"作为一等设计目标。**

这正是 HomeWAF 的切入点。

### 1.4 我们要解决的问题（按优先级）

| 编号 | 问题 | 现状 | HomeWAF 的目标 |
|---|---|---|---|
| P-1 | 家庭服务暴露公网后无人看守 | 裸奔或仅改密码 | 默认拒绝 + 全量攻击检测 + 自动封禁 |
| P-2 | 多服务多域名管理混乱 | 手工维护 Nginx 配置 | 声明式配置 + Web 控制台 + 自动证书 |
| P-3 | 企业级 WAF 误报高、调不动 | 需要 SecLang 专家 | 语义检测 + 一键加白 + 影子模式验证 |
| P-4 | 低功耗设备跑不动安全软件 | 动辄 1GB+ 内存 | 常驻内存 < 150MB，空闲 CPU < 1% |
| P-5 | 流量突增时设备直接雪崩 | 无背压，OOM 或全量超时 | 有界资源 + 等待池 + 分级降级 |
| P-6 | 被拦了不知道为什么 | 日志是原始规则命中 | 可解释命中：规则 + 语义证据 + 请求片段 |

### 2.3 关键技术事实核查

调研中有六个事实直接影响我们的技术选型，必须记录下来：

**事实一：纯 Rust 的 SecLang 引擎尚不可用于生产。**
crates.io 上的 `parapet`（发布名 `barbacane-waf`）是目前唯一公开的纯 Rust SecLang 规则引擎。它加载完整 OWASP CRS 后，通过 CRS 回归测试套件（go-ftw）的 **94.3%（3635/3853 个 stage）**，并且 `@detectSQLi`、`@detectXSS` 两个操作符仍无法编译。作者在 README 中明确写道："Do not deploy this: the remaining 5.7% is where the bypasses live"。这是一个诚实且重要的结论——**纯 Rust 路线目前无法直接继承 CRS 的规则供应链**。

**事实二：Rust 生态已有"代理 + 外挂安全 agent"的架构实践。**
`zentinel-proxy` 基于 Pingora 构建，把安全逻辑做成独立的 agent 进程（WAF agent、Policy agent、Auth agent 等），通过进程隔离实现故障隔离。其设计宣言强调"bounded resources、explicit failure modes、observable by default"——这与我们对"性能可预测性"的诉求高度一致，值得借鉴其**有界资源与显式失败模式**的设计哲学（但不必照搬其多进程 agent 架构，家用场景单进程更省资源）。

**事实三：雷池的检测率数据来自厂商自测，且样本集未公开。**
SafeLine README 给出的对比（33,669 个样本）：ModSecurity Level 1 检测率 69.74% / 误报率 17.58%；SafeLine Balance 检测率 71.65% / 误报率 0.07%；SafeLine Strict 检测率 76.17% / 误报率 0.22%。这组数据说明两件事：其一，**传统 CRS 在默认配置下的误报率高达 17.58%**，这正是家庭用户放弃它的核心原因；其二，**低误报是可以做到的**，但需要语义级检测而非纯正则。我们在 PRD 中把这组数字作为"误报率必须压到 0.1% 以下"的行业参照，而不是照抄其检测率承诺。

**事实四：ModSecurity 的 Rust 绑定依赖 C++ 工具链。**
`modsecurity` crate 是 libmodsecurity 的高层封装，要求系统预装 libmodsecurity >= 3.0.6。这违背"单二进制、零外部依赖、交叉编译到 ARM"的产品前提，因此**排除 FFI 路线**。

**事实五：规则供应链比引擎更重要，而规则可以"离线转换"而非"运行时兼容"。**
CRS 的 273 个 `@rx` 操作符中，实测 268 个可直接被 Rust `regex` 编译，5 个经词法修复后也可编译，**没有一个依赖 PCRE 独有的 lookaround 或反向引用**。这意味着"把 CRS 规则翻译成我们的 DSL"在技术上是可行的，瓶颈不在正则，而在流程控制（`skipAfter`）与状态变量（`tx.*`）。因此我们选择**离线转换 + 人工审核 + 影子验证**，而不是运行时解释 SecLang。详细设计见 `docs/rule-ingestion.md`。

**事实六：雷池基于 Nginx，且官方明确宣称"无规则引擎"。这两点既是它的优势，也是它的边界。**
雷池官网原文："无规则引擎，线性安全检测算法""平均检测延迟 < 1 毫秒，单核轻松检测 2000+ TPS 并发""基于 Nginx 开发"。这意味着三件事：

1. **语义引擎确实能做到低误报**（厂商称 0.07%），验证了我们"语义为主、正则为辅"的路线是对的。
2. **纯语义无法满足"用户要写规则"的需求**。没有规则引擎，用户只能配 URL 级简单规则，无法表达"当 UA 含 sqlmap 且路径是 /admin 且参数含 union 时阻断"这类组合条件。这是我们的差异化空间——**双引擎**，语义负责通用检测，DSL 负责业务定制。
3. **基于 Nginx 意味着拿不到 accept 层的控制权**，做不了真正的准入背压。我们的等待池与五级降级是对 Nginx 架构限制的直接回应。

同时必须承认：雷池在成熟度（40 万+ 部署）、开箱即用、动态防护（HTML/JS 加密）、生态集成（MCP/K8s/Kong）上明显领先，这些不是短期内能追上的。

### 2.4 竞品启示总结

| 启示 | 来源 | 我们的决策 |
|---|---|---|
| 正则规则集必然高误报 | ModSecurity CRS 17.58% 误报 | 语义分析作为主力，正则为兜底 |
| 纯 Rust 无法直接吃 CRS | parapet 94.3% | 自研规则 DSL，不承诺 CRS 兼容，但提供规则迁移工具 |
| 有界资源比极限性能更重要 | zentinel 设计宣言 | 引入等待池与分级降级 |
| 单容器部署是家用刚需 | BunkerWeb/雷池的多容器痛点 | 单二进制 + 内嵌 SQLite |
| 可解释性是极客用户的核心诉求 | 雷池闭源引擎的争议 | 每次拦截都给出证据链 |
| **纯语义无法满足规则定制** | 雷池"无规则引擎" | **双引擎**：语义负责通用检测，DSL 负责业务定制 |
| **语义能做到极低误报** | 雷池 0.07% 误报 | 语义为主力，正则为兜底，目标 < 0.1% |

## 3. 产品定位

### 3.1 一句话定义

> HomeWAF 是一款用 Rust 编写的单二进制反向代理型 Web 应用防火墙，为家庭 NAS、自建服务和智能家居中枢提供"开箱即用、低误报、可解释"的七层防护。

### 3.2 目标用户

| 用户画像 | 特征 | 核心诉求 | 占比预估 |
|---|---|---|---|
| **极客自建者** | 有 NAS/软路由，跑 Docker，懂基本网络 | 功能全、可配置、可审计、性能可控 | 55% |
| **技术型家庭用户** | 会装套件但不懂 SecLang | 一键开启、别误拦、出事能看懂 | 35% |
| **小型工作室** | 3-10 人，有对外站点 | 多域名、证书自动化、访问控制 | 10% |

### 3.3 核心使用场景

**场景 A：NAS 远程访问加固（最高频）**
用户在群晖/威联通上跑 HomeWAF，只把 443 暴露到公网（IPv6 或 IPv4），NAS 管理界面、相册、Drive 全部走域名访问。HomeWAF 负责：自动申请证书、拦截扫描器与暴力破解、对管理后台强制二次认证、把攻击日志汇总到控制台。

**场景 B：家庭多服务统一入口**
一台 N100 小主机跑 HomeWAF，内网有 Home Assistant（8123）、Jellyfin（8096）、Gitea（3000）、笔记服务（8080）。通过 `ha.home.lan`、`media.home.lan` 等域名分流，统一 TLS，统一访问日志。外网通过 IPv6 直连或 Cloudflare Tunnel 回源。

**场景 C：临时对外服务**
用户想给朋友演示一个本地项目，开一个临时 vhost，设置 24 小时后自动失效、限制访问人数、开启人机验证。到期自动回收。

**场景 D：攻击复盘**
控制台显示"过去 24 小时拦截 1,842 次攻击，其中 SQL 注入 623 次、路径扫描 891 次、暴力破解 328 次"，点开任意一条能看到完整请求、命中的规则、语义分析证据，并可一键加白或永久封禁来源。

### 3.4 非目标（明确不做）

明确划出边界，避免范围蔓延：

- **不做透明网桥/网关模式**：不串接家庭网络出口，不处理非 HTTP 流量。家用环境下网桥模式的调试成本与断网风险不可接受。
- **不做企业级集群与多租户**：不提供多节点配置同步、租户隔离、SLA 保障。单机单管理员是设计前提。
- **不做云托管服务**：不运营 SaaS，不做流量中转。
- **不做完整 CDN**：缓存仅作为可选加速手段，不做全球节点、不做图片处理。
- **不做终端防护**：不扫描家庭电脑，不做 EDR。
- **不承诺 ModSecurity CRS 运行时兼容**：不实现 SecLang 解释器，不加载 `.conf` 文件。但**提供离线转换工具**，把 CRS 规则翻译成本产品的 DSL（见 6.6 与 `docs/rule-ingestion.md`）。这是"不做兼容"与"要规则"之间唯一可行的解。
- **不做 L4 DDoS 清洗**：家用带宽本身有限，L4 洪泛只能靠运营商，我们只做 L7 限流与应用层缓解。

### 3.5 产品原则

这六条原则在后续所有功能取舍中以"一票否决"的方式生效：

1. **默认安全（Secure by Default）**：未显式配置的域名一律拒绝，不返回任何后端指纹；管理面默认只监听本地回环。
2. **低误报优先于高检出**：宁可漏掉一个变形攻击，也不能拦掉用户孩子的照片上传。所有新检测器必须先在影子模式跑够样本才能转阻断。
3. **可预测优于极致**：性能不足时排队等待、按预算降级、明确拒绝，绝不允许无界内存增长或全量超时雪崩。
4. **可解释优于黑盒**：任何一次拦截都必须能回答"哪条规则、匹配了什么、为什么判定为恶意"。
5. **零外部依赖**：单个二进制文件 + 一个 SQLite 文件 + 一个 YAML 配置，`scp` 上去就能跑，交叉编译到 aarch64 无痛。
6. **不信任输入，包括自己的配置**：配置解析、规则编译、日志渲染全部按不可信数据处理，禁止 `unsafe`（极少数系统调用除外并需审计注释）。

## 4. 系统架构

### 4.1 架构总览

系统分为**数据面（Data Plane）**与**控制面（Control Plane）**两部分，二者在同一进程内以不同 Tokio 任务组运行，通过**不可变配置快照**解耦。

```
┌──────────────────────────────────────────────────────────────────────┐
│                          控制面 Control Plane                         │
│  ┌────────────┐  ┌────────────┐  ┌────────────┐  ┌───────────────┐  │
│  │ Web 控制台  │  │  REST API  │  │  CLI 客户端 │  │ 配置编译器     │  │
│  │ (内嵌静态)  │  │  (axum)    │  │  (clap)    │  │ YAML→Snapshot │  │
│  └─────┬──────┘  └─────┬──────┘  └─────┬──────┘  └───────┬───────┘  │
│        └───────────────┴───────────────┘                 │          │
│                        │                                 │          │
│                 ┌──────▼──────┐                  ┌───────▼───────┐  │
│                 │  SQLite     │◄─────────────────┤ 规则编译器     │  │
│                 │  (WAL 模式)  │  事件/审计/统计    │ DSL→Program   │  │
│                 └──────┬──────┘                  └───────┬───────┘  │
└────────────────────────┼─────────────────────────────────┼──────────┘
                         │ 写入事件                        │ ArcSwap 原子发布
┌────────────────────────▼─────────────────────────────────▼──────────┐
│                          数据面 Data Plane                            │
│                                                                       │
│  ┌──────────┐   ┌──────────┐   ┌──────────┐   ┌──────────────────┐  │
│  │ 监听层    │──►│ TLS 终结  │──►│ 路由层    │──►│ 安全检测流水线    │  │
│  │ v4/v6    │   │ rustls   │   │ SNI/Host │   │ ACL→限流→Bot→    │  │
│  │ SO_REUSE │   │ ACME     │   │ 路径匹配  │   │ 规则→语义→认证   │  │
│  └──────────┘   └──────────┘   └──────────┘   └────────┬─────────┘  │
│                                                         │            │
│  ┌──────────┐   ┌──────────┐   ┌──────────┐   ┌────────▼─────────┐  │
│  │ 观测层    │◄──│ 响应防护  │◄──│ 上游转发  │◄──│ 请求体流式检测    │  │
│  │ 日志/指标 │   │ DLP/脱敏 │   │ 连接池    │   │ (分块+有界缓冲)   │  │
│  └──────────┘   └──────────┘   └──────────┘   └──────────────────┘  │
│                                                                       │
│  资源治理：连接信号量 / 请求信号量 / 检测信号量 / 有界等待池 / 预算计时器  │
└───────────────────────────────────────────────────────────────────────┘
```

**关键设计决策：数据面不写数据库。** 数据面只读 `ArcSwap<RuntimeSnapshot>` 中的不可变快照，所有需要持久化的内容（攻击事件、访问日志、统计聚合）通过**有界 channel** 异步投递给控制面的写入任务。这样做的原因：

1. SQLite 写入会产生锁竞争与 fsync 抖动，绝不能出现在请求热路径上；
2. 数据面可以完全无状态，便于将来做多进程 SO_REUSEPORT；
3. channel 有界，数据库写不动时通过丢弃低优先级日志（而非阻塞请求）实现背压隔离。

### 4.2 请求处理流水线

每个请求经过 7 个阶段，任一阶段可短路（拦截/重定向/直接响应）。阶段划分参考 ModSecurity 的 phase 模型，但做了合并与简化：

| 阶段 | 名称 | 处理内容 | 可短路 |
|---|---|---|---|
| S0 | 接入（Connect） | TCP accept、连接数限流、PROXY protocol 解析、超时设置 | 是（连接拒绝） |
| S1 | 传输（Transport） | TLS 握手、SNI 提取、ALPN 协商、客户端证书校验 | 是（握手失败） |
| S2 | 路由（Route） | Host/SNI 匹配 vhost、路径前缀匹配、上游选择、方法白名单 | 是（404/421/拒绝） |
| S3 | 请求头（ReqHeaders） | ACL（IP/GeoIP/UA/Referer）、限流、Bot 识别、认证、头部规则检测 | 是 |
| S4 | 请求体（ReqBody） | 流式读取 + 有界缓冲、Content-Type 解析、语义检测、文件上传校验 | 是（中途拦截） |
| S5 | 响应头（RespHeaders） | 响应头加固、敏感头剥离、CSP 注入、状态码策略 | 否（仅修改） |
| S6 | 响应体（RespBody） | 流式 DLP、敏感信息脱敏、错误页替换、内容长度校验 | 是（截断） |

**流式与缓冲的取舍**：请求体默认采用"边读边检、有界缓冲"。缓冲上限默认 1MB（可配，最大 16MB），超过上限时：
- 若该路由开启 `inspect_large_body`，转为**流式分块检测**（对每个 chunk 独立做语义分析，跨块状态保留有限窗口）；
- 否则跳过深度检测，仅做大小与类型校验，并记一条 `body_skipped` 审计事件。

这个策略是为了避免"上传一个 4GB 的 NAS 备份文件导致 WAF OOM"这类家用场景的典型事故。

### 4.3 配置热更新机制

配置变更不允许重启进程，也不允许请求看到"半个新配置"。

```
YAML 文件变更 / API 提交
        │
        ▼
  ┌──────────────┐   校验失败则整体回滚
  │ 解析 + 校验   │──────────────────────► 返回错误，旧快照继续服务
  └──────┬───────┘
         ▼
  ┌──────────────┐
  │ 编译为快照    │  规则预编译、正则预编译、路由表构建、证书加载
  │ (不可变)      │  编译耗时目标 < 100ms
  └──────┬───────┘
         ▼
  ┌──────────────┐
  │ ArcSwap.store│  原子替换，读者无锁
  └──────┬───────┘
         ▼
  正在处理的请求继续用旧快照（Arc 引用计数保证生命周期）
  新请求立即使用新快照
```

**为什么用 ArcSwap 而不是 RwLock**：读路径完全无锁、无原子争用，热路径开销接近于零；写路径极少发生，代价可以忽略。这是 Rust 生态里处理"读多写极少"配置的标准做法。

**配置版本与回滚**：每次成功发布生成一个递增 `revision`，SQLite 保留最近 50 个版本的完整快照，支持 `homewaf config rollback <rev>` 一键回滚。

### 4.4 并发模型与自适应容量（等待池）

这是本产品区别于其他 WAF 的核心设计，也是用户明确提出的诉求："性能可以自己控制，不行就等待池"。

#### 4.4.1 资源分层

系统把资源分成四层，每层独立限额，任一层饱和都不会导致整体崩溃：

| 层级 | 资源 | 默认上限 | 超限行为 |
|---|---|---|---|
| L1 连接 | 并发 TCP 连接数 | 4096（按内存自动调整） | 拒绝新 accept，发送 RST |
| L2 请求 | 并发在途请求数 | 512 | 进入等待池 |
| L3 检测 | 并发检测任务数 | CPU 核数 × 2 | 进入等待池（检测队列） |
| L4 上游 | 每上游并发连接数 | 128（可配） | 排队或快速失败 |

#### 4.4.2 等待池设计

等待池不是简单的 `Semaphore::acquire()` 阻塞，而是**带优先级、带超时、带水位观测的有界队列**：

```
请求到达
   │
   ├─► 尝试立即获取令牌 ──成功──► 进入处理
   │
   └─► 失败
        │
        ├─► 等待池未满（< capacity）──► 入队，等待 min(排队超时, 剩余预算)
        │                                   │
        │                                   ├─ 拿到令牌 ──► 继续处理
        │                                   └─ 超时 ─────► 503 + Retry-After
        │
        └─► 等待池已满 ──► 立即 503（快速失败，不占用内存）
```

**参数默认值与依据**：

| 参数 | 默认值 | 说明 |
|---|---|---|
| `queue_capacity` | 1024 | 按 1KB/请求的元数据估算，约 1MB 内存 |
| `queue_timeout` | 200ms | 家庭场景用户对延迟极敏感，超过 200ms 的等待不如直接失败 |
| `request_timeout` | 30s | 含上游，大文件下载路由单独配置 |
| `detect_budget` | 50ms | 单个请求的检测时间预算，超预算触发降级 |
| `queue_high_watermark` | 70% | 触发降级的队列水位 |
| `queue_low_watermark` | 40% | 解除降级的水位（滞回，防抖） |

**优先级**：等待池支持两级优先级。管理面请求、健康检查、已认证会话为高优先级；匿名请求为普通优先级。高优先级队列独立配额（默认 64），保证在攻击洪峰下管理员仍能打开控制台——这一点在企业 WAF 里常被忽略，家庭用户被打了之后连控制台都打不开，体验极差。

#### 4.4.3 五级降级梯度

当系统压力上升时，不是"要么全检要么不检"，而是按梯度逐级卸载：

| 级别 | 触发条件 | 行为 | 安全影响 |
|---|---|---|---|
| **L0 正常** | 水位 < 70% | 全量检测（请求+响应+语义） | 无 |
| **L1 轻载** | 水位 ≥ 70% 或 P99 检测 > 30ms | 跳过响应体 DLP 与内容脱敏 | 响应方向防护减弱 |
| **L2 中载** | 水位 ≥ 85% 或 P99 检测 > 50ms | 跳过深度语义分析，仅走规则引擎 + ACL | 变形攻击检出率下降 |
| **L3 重载** | 水位 ≥ 95% 或内存 > 85% | 仅保留 ACL + 限流 + 已知恶意 IP 拦截 | 仅剩粗粒度防护 |
| **L4 过载** | 队列满 或 内存 > 95% | 新连接直接 503，保留已有连接 | 拒绝服务（但是受控的） |

**关键约束**：降级只允许发生在"检测深度"维度，**绝不允许跳过 ACL 与限流**。因为这两项是 O(1) 复杂度的，跳过它们既不能省资源，又会打开最危险的口子。

**降级必须可见**：每次降级/恢复都写审计事件并在控制台顶部显示横幅"当前处于 L2 降级模式，部分深度检测已暂停"。偷偷降级是安全产品的大忌。

**fail-open / fail-closed 可配置**：默认 `fail-closed`（检测超预算则拒绝），但对"媒体流""大文件下载"等路由可单独设为 `fail-open`（放行并记事件）。这是家用场景的必要妥协——没人希望因为 WAF 检测超时导致正在看的电影卡死。

#### 4.4.4 预算传播（Deadline Propagation）

每个请求在进入时计算一个绝对截止时间 `deadline = now + request_timeout`，并向下传递。各阶段只能使用"剩余预算"：

```
剩余预算 = deadline - now
检测阶段可用预算 = min(detect_budget, 剩余预算 × 0.5)
上游可用预算 = 剩余预算 - 已消耗
```

任何阶段发现剩余预算 ≤ 0，立即按该路由的 fail 策略处理，不再继续。这避免了"检测花了 3 秒、上游再花 30 秒"的叠加超时。

### 4.5 进程与线程模型

| 项 | 设计 |
|---|---|
| 进程数 | 1（单进程） |
| 运行时 | Tokio 多线程 runtime（Pingora 内部同样基于 Tokio，二者共用同一 runtime） |
| Worker 线程 | `min(available_parallelism, 8)`，ARM 双核设备上为 2 |
| 阻塞线程池 | 4（用于 SQLite 写入、文件 IO、证书读写） |
| 控制面任务 | 独立 Tokio task，与数据面共享 runtime 但独立限额 |
| 内存分配器 | mimalloc（ARM 上相比 glibc malloc 有 10-20% 吞吐提升，碎片更少） |
| 优雅退出 | 收到 SIGTERM 后停止 accept，等待在途请求完成（最长 10s），flush 事件队列，退出 |

**为什么不做多进程 SO_REUSEPORT**：家用设备通常 2-4 核，多进程带来的配置同步、证书共享、统计聚合复杂度远超收益。单进程多线程已能打满千兆。架构上保留 `--workers N` 的扩展点，v2 再考虑。

### 4.6 代理层选型：为什么不是 Nginx，也不是裸 Hyper

这一节回答一个必须回答的问题：**流量处理层用什么？** 结论是 **Pingora**，理由不是"它最快"，而是"它最不容易写错"。

#### 4.6.1 先把家庭场景的性能账算清楚

很多"性能不达标"的焦虑，来自把企业级指标套到家庭场景上。

| 项 | 数值 | 推导 |
|---|---|---|
| 千兆宽带实际吞吐 | 940 Mbps ≈ 117.5 MB/s | 扣除协议开销 |
| 平均请求 + 响应 | 1 KB + 4 KB = 5 KB | 家庭 Web 场景典型值 |
| **理论上限** | **≈ 23,500 RPS** | 117.5 MB/s ÷ 5 KB |
| 家庭实际峰值 | **< 3,000 RPS** | 4K 视频占 25 Mbps，其余为网页与 API |
| 单核 Rust 代理能力 | 8,000-15,000 RPS | 实测区间 |
| 4 核 N100 能力 | 25,000+ RPS | 已超千兆线速 |

**结论：硬件能力是需求的 8 倍以上。转发性能不是瓶颈，而且永远不会是。**

家庭 WAF 真正的性能挑战只有两个，且都不在"每秒多少请求"上：

1. **大文件传输**（NAS 备份、4K 视频）——需要零拷贝，Pingora 原生支持
2. **检测延迟**——单请求 1-5ms，用户可感知

#### 4.6.2 真正的瓶颈在检测层，不在转发层

| 阶段 | 单请求耗时 | 触发比例 | 加权耗时 |
|---|---|---|---|
| 代理转发（Pingora） | ~25 μs | 100% | 25 μs |
| 预过滤（Aho-Corasick） | ~50 μs | 100% | 50 μs |
| 规则引擎（1000 条） | ~200 μs | 5% | 10 μs |
| 语义引擎 | ~2 ms | 1% | 20 μs |
| **合计** | — | — | **≈ 105 μs** |

代理层占 24%。即使把代理层优化到 0，总延迟也只降四分之一；而如果代理层实现有缺陷（连接池泄漏、HTTP/2 流控错误），延迟会翻几倍。

**所以优化顺序应该是：检测层 → 连接复用 → 代理层微优化。** 反过来做是浪费。

#### 4.6.3 三个方案的真实对比

| 维度 | Nginx + 模块/进程 | 裸 Hyper 自研 | **Pingora** |
|---|---|---|---|
| 转发性能 | 高（成熟） | **取决于实现质量**，可能很高也可能很差 | 高（优于 Nginx） |
| 连接池 | 按 worker 隔离，无法跨 worker 复用 | 自己写，容易写错 | **全局共享，跨线程复用** |
| 健康检查/负载均衡 | 开源版只有被动检查 | 自己写 | 内置主动+被动 |
| 优雅重启（零丢连接） | 支持 | **极难正确实现** | 内置 |
| HTTP/2 流控 | 成熟 | **容易踩坑** | 成熟 |
| 慢连接攻击防护 | 需额外配置 | 自己写 | 内置超时体系 |
| 请求体流式检测 | 模块/Lua 层很别扭 | 完全可控 | `request_body_filter` 逐块回调，**官方文档明确提到可执行 WAF 规则** |
| 等待池/accept 层控制 | **拿不到** | 完全可控 | 可控（自定义 listener） |
| 部署形态 | **两组件 + IPC** | 单二进制 | 单二进制 |
| 正确性风险 | 低 | **高**（3-6 个月才能稳定） | 低（生产验证） |
| 依赖 | C + 独立进程 | 纯 Rust | 纯 Rust（TLS 除外） |

**Nginx 方案被否决的三个硬理由**：

1. **部署退化**：变成 Nginx + WAF 进程 + IPC，违背"单二进制"这一产品前提。家庭用户装两个东西的失败率远高于装一个。
2. **拿不到关键控制权**：等待池需要在 accept 层做准入（见 4.4），Nginx 不暴露这个钩子；body 流式检测在模块层要处理复杂的缓冲区生命周期。
3. **性能反而更差**：跨进程传 body 的拷贝成本，高于单进程内检测。

**裸 Hyper 方案被否决的理由**：不是性能，是**正确性**。连接池、HTTP/2 流控、优雅重启、TLS 会话复用、慢连接防护——这些每个都有大量边界情况，自己写到生产级需要 3-6 个月，而且 bug 往往直接变成安全漏洞。Pingora 已经把这些做完了。

#### 4.6.4 关于 Cloudflare "手搓" 这件事

用户的直觉是对的：Cloudflare 确实手搓了。但他们手搓的**成果已经开源成 Pingora**（2024 年 2 月）。

我们不需要重走一遍。Cloudflare 当年的处境是"没有可用的框架"，我们的处境是"有一个被 4000 万 RPS 验证过的框架"。

**但必须诚实说明 Cloudflare 性能数据的归因**，否则会误导决策：

| 指标 | 官方数据 | **真实归因** |
|---|---|---|
| CPU 降低 70% | 相对其旧 Nginx/OpenResty 服务 | **主要来自连接复用率从 87.1% 提升到 99.92%**，减少 TLS 握手；其次是消除 C/Lua 之间的拷贝与 GC。**不是"Rust 比 C 快 70%"** |
| 内存降低 67% | 同上 | 共享连接池 + 更少的每连接状态 |
| TTFB 中位数 -5ms | 全站 | 连接复用省下的握手时间 |
| TTFB P95 -80ms | 全站 | 同上，长尾受益更明显 |

对我们的启示：**Pingora 的性能优势在"高连接复用率"场景才显著**。家庭场景连接数少、复用率天然高，所以性能收益远没有 70% 那么夸张。选它的核心理由依然是**工程正确性**，性能只是顺带。

#### 4.6.5 代价与缓解

| 代价 | 缓解 |
|---|---|
| Pingora 不支持 HTTP/3 | v1.0 不交付 HTTP/3，延后至 v1.2；需要时在监听层旁路 quinn |
| rustls 后端标注 experimental | 优先接入；受阻时数据面暂用 BoringSSL，发布说明标注；控制面始终 rustls |
| 0.x 版本 API 可能变动 | 锁定 minor 版本；在 `ProxyEngine` trait 后封装，保留切换回 Hyper 的可能 |
| 编译体积与时间增加 | LTO + strip；CI 缓存 |

**架构保险**：数据面不直接依赖 Pingora 类型，而是定义自己的 `ProxyEngine` trait（`serve`、`shutdown`、`reload_tls`）。Pingora 作为默认实现。这样即使将来要换回 Hyper 或换别的框架，改动被限制在一个 crate 内。

## 6. 检测引擎设计（核心）

这是整个产品的技术核心。设计目标是：**语义分析承担主要检出，规则引擎承担快速拦截与业务定制，二者共享评分与动作体系。**

### 6.1 双引擎协作模型

```
请求负载
   │
   ├─►【第一层】快速预过滤（< 50μs）
   │     Aho-Corasick 多模式匹配 + 长度/字符集启发式
   │     作用：用字面量（"union select"、"<script"、"../"、"${"）快速排除 90%+ 的良性请求
   │     未命中 → 直接放行（仅记访问日志），不进入后续检测
   │
   ├─►【第二层】规则引擎（< 200μs）
   │     执行用户自定义规则 + 内置签名规则
   │     输出：命中规则列表 + 分值
   │
   └─►【第三层】语义引擎（< 2ms，可降级跳过）
         对可疑负载做词法/语法/上下文分析
         输出：confidence + evidence[]
   │
   ▼
  评分聚合 → 阈值判定 → 动作执行（放行/记录/挑战/阻断）
```

**为什么要三层**：家庭设备的 CPU 预算极低，不可能对每个请求都做完整语义分析。预过滤把"明显干净"的请求（静态资源、图片、正常 API 调用）快速放行，把 CPU 留给真正可疑的 1%-5% 流量。这是把"低功耗"和"高检出"同时做到的关键。

**降级时的行为**：L2 降级跳过第三层，仅保留前两层。因此前两层必须自身足够强——这也是我们把"内置签名规则"做厚的理由。

### 6.2 规则 DSL

#### 6.2.1 设计目标

- 人类可读，非安全专家也能改
- 编译期校验，写错立即报错而非静默失效（吸取 parapet 的教训：**不认识的结构必须报错，绝不跳过**）
- 支持组合、优先级、例外抑制
- 可版本化、可 diff、可 Git 管理

#### 6.2.2 语法示例

```yaml
# rules/sqli.yaml
version: 1
rules:
  - id: HW-1001
    name: SQL 注入 - 联合查询注入
    severity: critical          # info | low | medium | high | critical
    tags: [owasp-a03, sqli]
    phase: request_body         # request_headers | request_body | response_headers | response_body
    targets:                    # 检测对象
      - args                    # 所有查询参数与表单字段
      - body.json               # JSON body 的所有字符串叶子节点
      - headers.cookie
    match:
      any:
        - semantic: sqli        # 调用语义检测器
        - regex: '(?i)\bunion\b\s+(?:all\s+)?\bselect\b'
    action: block               # block | challenge | log | score | rewrite | tag
    score: 60
    message: "检测到 SQL 联合查询注入"
    # 例外：降低误报的关键
    exceptions:
      - host: "notes.home.lan"
        path: "/api/search"
        param: "q"
        reason: "笔记全文搜索允许输入 SQL 关键字"
        expires: 2027-01-01
```

#### 6.2.3 匹配器（Matcher）

| 匹配器 | 语法 | 说明 |
|---|---|---|
| `semantic` | `semantic: sqli` | 调用语义检测器，可选 `min_confidence: 0.7` |
| `regex` | `regex: '...'` | 线性时间正则，编译期校验 |
| `contains` | `contains: ["../", "..\\"]` | 字面量，走 Aho-Corasick |
| `prefix` / `suffix` | `prefix: "/admin"` | 前缀/后缀 |
| `cidr` | `cidr: ["10.0.0.0/8", "fd00::/8"]` | IP 段匹配 |
| `geoip` | `geoip: { country: [CN, US] }` | 需加载 GeoLite2 |
| `method` | `method: [PUT, DELETE]` | HTTP 方法 |
| `header` | `header: { name: "User-Agent", regex: "sqlmap" }` | 头部匹配 |
| `size` | `size: { gt: 10485760 }` | 体积阈值 |
| `rate` | `rate: { key: ip, count: 100, window: 60s }` | 限流匹配器 |
| `expr` | `expr: 'len(body) > 1024 && status == 200'` | 轻量表达式（自研 AST，非通用脚本） |

#### 6.2.4 组合子

```yaml
match:
  all:                  # 与
    - method: [POST]
    - any:              # 或
        - semantic: xss
        - contains: ["<script"]
    - not:              # 非
        - cidr: ["192.168.1.0/24"]
```

嵌套深度限制 8 层，节点总数限制 256，防止规则本身成为 DoS 向量。

#### 6.2.5 动作

| 动作 | 行为 |
|---|---|
| `log` | 仅记录，不干预（影子模式用） |
| `score` | 累加异常分，达到阈值才阻断 |
| `block` | 立即阻断，返回配置的错误页（默认 403） |
| `challenge` | 返回人机验证页（JS/Cookie/PoW） |
| `rewrite` | 重写请求（如剥离危险参数） |
| `tag` | 打标签供后续规则引用 |
| `redirect` | 302 到指定地址 |
| `tarpit` | 极慢响应（消耗攻击者连接，慎用） |

#### 6.2.6 评分模型

采用改进的异常评分（Anomaly Scoring）：

```
总分 = Σ(规则分值 × 规则权重) + Σ(语义置信度 × 语义权重)

判定：
  0        → 放行
  1-4      → 记录（info 级日志）
  5-9      → 记录 + 标记（进入观察名单）
  10-24    → 挑战（人机验证）
  ≥ 25     → 阻断
```

阈值可按 vhost 覆盖。例如 NAS 管理后台可以把阻断阈值降到 10（严格），家庭相册可以升到 30（宽松）。

**为什么用累加分而不是单条命中即阻断**：单条命中即阻断必然高误报。多个弱信号叠加（比如"UA 是 sqlmap" + "参数含 union select" + "路径是 /admin"）比单个强信号更可靠。

### 6.3 语义检测器

每个检测器实现统一 trait：

```rust
pub trait Detector: Send + Sync {
    fn name(&self) -> &'static str;
    /// 返回 None 表示未发现异常；Some 表示命中，携带置信度与证据
    fn detect(&self, ctx: &RequestContext, payload: &Payload) -> Option<Detection>;
}

pub struct Detection {
    pub confidence: f32,        // 0.0 - 1.0
    pub evidence: Vec<Evidence>,
}

pub struct Evidence {
    pub offset: usize,          // 在原始 payload 中的字节偏移
    pub snippet: String,        // 截断后的片段（最多 128 字节）
    pub reason: &'static str,   // 人类可读原因
    pub ast_path: Option<String>, // 语法树路径，用于解释
}
```

#### 6.3.1 SQL 注入检测器

**不用正则，用词法 + 语法状态机。**

处理流程：
1. **归一化**：URL 解码（最多 3 层，防多重编码绕过）→ Unicode NFKC 归一化 → 注释剥离（`/**/`、`--`、`#`）
2. **词法分析**：切分为 `String`、`Number`、`Keyword`、`Operator`、`Comment`、`Function`、`Punctuation`
3. **语法模式识别**，重点识别以下高危结构：

| 模式 | 特征 | 置信度 |
|---|---|---|
| 闭合 + 注释 | 字符串引号提前闭合，后接 `--` / `#` / `/*` | 0.95 |
| 布尔恒真 | `' OR '1'='1`、`OR 1=1`、`OR 'a'='a'` | 0.95 |
| 联合查询 | `UNION [ALL] SELECT` 且列数对齐 | 0.90 |
| 堆叠查询 | `;` 后接第二条语句 | 0.90 |
| 时间盲注 | `SLEEP()`、`BENCHMARK()`、`pg_sleep()`、`WAITFOR DELAY` | 0.92 |
| 报错注入 | `EXTRACTVALUE()`、`UPDATEXML()`、`GTID_SUBSET()` | 0.85 |
| 文件读写 | `LOAD_FILE()`、`INTO OUTFILE`、`xp_cmdshell` | 0.90 |
| 系统表探测 | `information_schema`、`sysobjects`、`pg_catalog` | 0.75 |

4. **反误报关键**：区分"结构"与"字面量"。用户搜索 `O'Reilly` 会产生一个未闭合的引号，但**不构成**闭合+注释结构，因此不命中。用户搜索 `union select 教程` 含关键字但缺少列数对齐与前置闭合，置信度降到 0.3 以下，不触发阻断。

#### 6.3.2 XSS 检测器

**按 HTML5 规范实现 tokenizer，追踪上下文。** 这是与正则方案的本质区别。

上下文类型与对应检测策略：

| 上下文 | 示例 | 检测重点 |
|---|---|---|
| HTML 文本 | `<div>USER_INPUT</div>` | 标签起始符 `<` + 合法标签名 + 事件属性 |
| 属性值（双引号） | `<a href="USER_INPUT">` | 引号闭合 + 新属性注入 |
| 属性值（无引号） | `<a href=USER_INPUT>` | 空格分隔的属性注入 |
| URL 上下文 | `href="javascript:USER_INPUT"` | `javascript:` / `data:` / `vbscript:` 协议 |
| JS 字符串 | `var x = 'USER_INPUT'` | 引号闭合 + 语句注入 |
| JS 表达式 | `<script>var x = USER_INPUT</script>` | 任意表达式即高危 |
| CSS | `style="color: USER_INPUT"` | `expression()`、`url()`、`@import` |
| 注释 | `<!-- USER_INPUT -->` | `-->` 提前闭合 |

**关键能力**：识别**分段注入**。例如 `<scr<ipt>alert(1)</scr<ipt>` 在朴素正则下不匹配 `<script`，但 tokenizer 在解析时会先遇到非法标签 `<scr<ipt>`，按 HTML5 错误恢复规则重建 token 流，从而识别出攻击意图。

#### 6.3.3 命令注入检测器

1. 识别 shell 元字符：`;` `|` `&` `$()` `` ` `` `${}` `>` `<` 换行
2. 对元字符后的片段做**命令词法分析**，判断是否构成"命令 + 参数"结构
3. 匹配高危命令白名单（`curl`、`wget`、`nc`、`bash`、`sh`、`powershell`、`certutil`、`chmod`）
4. 区分"包含分号的正常文本"与"分号后接可执行命令"

#### 6.3.4 路径遍历检测器

1. **多重解码**：URL 解码 → Unicode 解码 → 二次 URL 解码（检测 `%252e%252e%252f`）
2. **路径规范化**：按 POSIX 规则折叠 `..`、`.`、重复斜杠
3. **深度计算**：计算规范化后跳出根目录的层数
4. **变体识别**：`....//`、`..;/`、`..%c0%af`（UTF-8 超长编码）、Windows 反斜杠、ADS 流（`file.php::$DATA`）

#### 6.3.5 SSRF 检测器

1. 提取参数中的 URL（含 `http://`、`https://`、`file://`、`gopher://`、`dict://`）
2. 解析主机名，做 DNS 解析（可选，默认关闭以避免性能开销与 DNS 泄露）
3. 判定目标地址类别：回环、RFC1918 私网、链路本地（`169.254.0.0/16`，含云元数据 `169.254.169.254`）、CGNAT（`100.64.0.0/10`）、IPv6 ULA（`fc00::/7`）、IPv6 链路本地（`fe80::/10`）、IPv4 映射的 IPv6
4. 识别绕过手法：十进制 IP（`2130706433`）、八进制、十六进制、`0.0.0.0`、`[::]`、DNS 重绑定（需二次解析比对）

#### 6.3.6 其他检测器

| 检测器 | 核心方法 |
|---|---|
| **XXE** | XML 解析时检测 `<!DOCTYPE`、`<!ENTITY`、外部实体引用；禁用 DTD 处理 |
| **SSTI** | 识别模板表达式定界符（`{{ }}`、`{% %}`、`${ }`、`#{ }`）并对内部做表达式语法分析 |
| **LDAP 注入** | 识别 `)(`、`*`、`|`、`&` 构成的过滤器结构破坏 |
| **XPath 注入** | 识别 `' or '1'='1` 与 XPath 函数（`count()`、`string()`） |
| **NoSQL 注入** | JSON body 中出现 `$ne`、`$gt`、`$where`、`$regex` 等操作符 |
| **CRLF 注入** | 头部值中出现 `%0d%0a`、`\r\n` |
| **反序列化** | 识别 Java（`rO0AB`、`aced0005`）、PHP（`O:`、`a:`）、Python pickle（`\x80\x04`）、.NET（`AAEAAAD`）魔数 |
| **文件上传** | 魔数 vs Content-Type vs 扩展名三重校验；识别双扩展名（`shell.php.jpg`）、`.htaccess`、SVG 内嵌脚本 |
| **Webshell 特征** | 响应体中出现常见 webshell 函数组合（`eval($_POST`、`assert(`、`Runtime.getRuntime().exec`） |
| **敏感信息泄露** | 响应体正则匹配身份证、手机号、银行卡、私钥头（`-----BEGIN PRIVATE KEY-----`）、云 AK/SK 模式 |

### 6.4 归一化管线（防绕过的地基）

所有检测器共享一条归一化管线，顺序固定且**必须幂等**：

```
原始字节
  → 长度校验（超限截断并标记）
  → 字符集判定（UTF-8 校验，非法序列按 replacement 处理）
  → 百分号解码（最多 3 层，每层记录是否发生变化）
  → Unicode NFKC 归一化（防全角/兼容字符绕过）
  → 大小写折叠（仅在检测副本上做，不影响转发）
  → 空白归一化（\t \r \n → 空格，仅用于模式匹配）
  → NUL 字节剔除
  → 输出：NormalizedPayload { raw, decoded, normalized, flags }
```

**每一层转换都记录 flag**（如 `multi_encoded`、`contains_nul`、`invalid_utf8`），这些 flag 本身参与评分——一个正常请求不应该出现"三层编码 + NUL 字节"。

### 6.5 可解释性输出

每次拦截生成如下结构（控制台直接渲染）：

```json
{
  "event_id": "01J8X...",
  "time": "2026-10-22T10:15:33.482+08:00",
  "host": "nas.home.lan",
  "client_ip": "2408:8207:1234::5678",
  "method": "POST",
  "path": "/api/login",
  "action": "block",
  "score": 85,
  "matched_rules": [
    { "id": "HW-1001", "name": "SQL 注入 - 联合查询注入", "score": 60 }
  ],
  "semantic_findings": [
    {
      "detector": "sqli",
      "confidence": 0.93,
      "reason": "字符串引号提前闭合，后接注释符，构成典型注入结构",
      "evidence": {
        "offset": 42,
        "snippet": "admin' --",
        "ast_path": "BinaryExpr[0].StringLit.close → Comment"
      }
    }
  ],

```

这段结构就是"可解释"的具体含义：不只知道"被拦了"，还知道"在哪、因为什么语法结构、经过几层编码"。

### 6.6 规则来源与适配（前期能力的关键）

自研规则库不可能在第一天就覆盖全部攻击面。产品早期的规则供给必须依赖外部来源，但**不能走"运行时兼容"路线**（见 2.3 事实一）。我们采用**离线转换**：

```
外部规则源 ──► 格式识别 ──► Parser ──► 统一 IR ──► Mapper ──► 我们的 DSL
                                                              │
                                          覆盖率报告 ◄─────────┤
                                          人工审核   ◄─────────┤
                                          影子验证   ◄─────────┘
```

**统一 IR（中间表示）** 是整个子系统的核心：N 个来源只需 N 个 Parser，目标 DSL 只需 1 个 Mapper。IR 显式表达"不支持"的结构，转换器遇到不认识的内容**必须报错并记录，绝不静默跳过**——静默跳过等于制造绕过。

**规则来源优先级**：

| 优先级 | 来源 | 转换难度 | 预期自动转换率 | 价值 |
|---|---|---|---|---|
| P0 | IP/CIDR 列表（雷池 IP 组、Spamhaus） | 极低 | 100% | 立竿见影，M0 即可交付 |
| P0 | OWASP CRS（SecLang） | 高 | 75-85%（估算） | 覆盖主体攻击面 |
| P1 | Coraza 规则集 | 高 | 同上 | 同 CRS |
| P2 | Naxsi / AWS WAF | 中 | 60-70% | 补充 |
| P3 | Cloudflare 表达式 / Snort | 中高 | 30-50% | 按需 |

**规则质量分级**（导入的规则不能与自研规则平权）：

| 级别 | 来源 | 默认状态 |
|---|---|---|
| A | HomeWAF 自研核心 | 启用，阻断 |
| B | 外部转换 + 通过回归语料 | 启用，阻断 |
| C | 外部转换，未验证 | **启用，仅记录**（影子模式 7 天） |
| D | 转换待人工确认 | 禁用 |
| E | 外部订阅（IP 组） | 启用，按配置动作 |

**默认策略：任何导入规则先进 C 级**，跑满 7 天且零误报才升为 B 级。这是"低误报优先"原则在规则层面的落地。

**IP 组订阅的实测结论**（对真实雷池分享链接抓取分析）：

| 项 | 实测值 | 对设计的影响 |
|---|---|---|
| 总条数 | 578 | 数据量小，但按 10 万条设计 |
| IPv4 / IPv6 | 305 / **273** | IPv6 占 47%，双栈是硬需求 |
| IPv6 前缀分布 | /28 ×1、/62 ×3、/63 ×42、/64 ×227 | 以 /64 为主 |
| 超宽前缀 | `240d:c010::/28`（覆盖 2^100 地址） | **必须设置前缀长度下限护栏** |

订阅外部列表本质上是把别人的封禁决策直接应用到自己的网络，因此护栏是强制项：拒绝 `/0`、IPv4 前缀不小于 `/8`、IPv6 不小于 `/32`、单次变更幅度超 50% 暂停应用、仅允许 HTTPS、SSRF 防护、首次导入默认 dry-run。

> 完整设计（IR 定义、SecLang 映射表、覆盖率报告、护栏阈值、规则包格式）见 **`docs/rule-ingestion.md`**。

### 7.2 应用与路由

> **核心概念：应用（Application）**。一个应用 = 一个对外服务 = 一个域名。这是比"站点"更贴合用户心智的组织单元——用户想的是"我的相册"，不是"vhost"。一个应用可包含 1 个主域名 + N 个别名、1..N 个上游（多端口）、0..N 个路由（路径分流）。

| 编号 | 需求 | 优先级 | 验收标准 |
|---|---|---|---|
| FR-RT-025 | **应用模型（三层结构）** | P0 | 应用 = 域名（1 主 + N 别名）+ 上游组（1..16 个，可多端口/多主机）+ 路由（0..N 个路径规则）；三层正交，复杂度按需增加 |

#### 7.5.2 观察模式（Observe Mode）

首次部署时，用户不知道自己的业务会不会被误拦。观察模式让整个 WAF 先"只看不动"，用真实流量评估误报。

**与单类 `monitor` 的区别**：`monitor` 是逐类设置，用于单条规则上线；观察模式是一个开关，用于整机首次部署或大版本升级。

**不在观察范围内的能力**（始终生效）：

| 能力 | 受观察模式影响 | 理由 |
|---|---|---|
| 规则引擎阻断 | 是（降级为记录） | 主要观察对象 |
| 语义引擎阻断 | 是（降级为记录） | 主要观察对象 |
| ACL 黑名单 | **否** | 用户显式配置的封禁，不该被观察取消 |
| 限流 | **否** | 否则观察期会被打挂 |
| 认证 | **否** | 同上 |

**核心产出**是"若阻断会拦掉多少请求"这个数字——它让用户在开启阻断前就知道影响面。报告同时给出误报 Top 3 与一键加白建议。

**UI 强制要求**：观察模式开启期间，控制台顶部持续显示横幅（含剩余天数与已拦截计数）。用户开了忘记关是这类产品最常见的安全事故，横幅 + 到期自动关闭是双重保险。

## 9. 安全设计（WAF 自身的安全）

WAF 是网络边界上权限最高的组件，它自己被攻破的后果比被保护的应用被攻破更严重——攻击者可以直接读取所有明文流量、篡改转发内容。因此本章与功能需求同等重要。

### 9.1 威胁模型（STRIDE）

| 威胁 | 具体场景 | 对策 |
|---|---|---|
| **Spoofing（伪造）** | 伪造 X-Forwarded-For 绕过 IP 封禁 | 仅信任配置的代理 CIDR；从右向左解析；不可信来源的 XFF 头直接丢弃 |
| **Tampering（篡改）** | 篡改配置文件或数据库植入恶意规则 | 配置文件权限 0600；数据库文件权限 0600；配置变更全量审计；可选签名校验 |
| **Repudiation（抵赖）** | 管理员否认做过某次变更 | 审计日志记录操作者、时间、IP、变更前后 diff，日志只追加不可改 |
| **Information Disclosure（信息泄露）** | 错误页泄露堆栈；日志泄露密码；控制台泄露拓扑 | 统一错误页；日志字段级脱敏；控制台不展示上游内网地址（可配） |
| **Denial of Service（拒绝服务）** | 构造超长 URL/超多参数/超深 JSON 打爆 WAF | 全维度大小限制；解析深度限制；有界队列；预算超时 |
| **Elevation of Privilege（提权）** | 通过规则注入执行任意代码 | 规则 DSL 是声明式 AST，**不可执行任意代码**；WASM 插件沙箱化并限制资源 |

### 9.2 攻击面清单与加固

| 攻击面 | 风险 | 加固措施 |
|---|---|---|
| **HTTP 解析器** | 请求走私、解析歧义 | 严格 RFC 9112 校验；拒绝双 `Content-Length`；拒绝 `CL`+`TE` 并存；拒绝非法 header 名；限制 header 数量（100）与总大小（32KB） |
| **TLS 实现** | 降级、弱套件 | rustls（内存安全）；仅 AEAD；禁用重协商；禁用压缩（CRIME） |
| **规则引擎** | ReDoS、规则注入 | 只用 `regex` crate（线性时间）；规则编译期校验；嵌套深度 ≤ 8；节点数 ≤ 256 |
| **配置解析** | YAML 炸弹、路径穿越 | 限制 YAML 别名展开；限制文件大小；`include` 路径必须在配置目录内（防 `../../etc/passwd`） |
| **管理 API** | 未授权访问、CSRF、越权 | 默认仅监听 `127.0.0.1` + Unix Socket；强制认证；CSRF Token；SameSite=Strict；敏感操作二次确认 |
| **Web 控制台** | XSS、点击劫持 | 严格 CSP（`default-src 'self'`）；前端框架默认转义；`X-Frame-Options: DENY`；不使用 `innerHTML` |
| **SQLite** | SQL 注入 | 全部使用参数化查询；不使用字符串拼接 SQL |
| **日志** | 日志注入（CRLF） | 结构化 JSON 输出；控制字符转义；单条日志长度上限 |
| **文件上传（证书/规则）** | 路径穿越、符号链接攻击 | 文件名白名单校验；禁止符号链接；写入使用 `O_NOFOLLOW` |
| **插件（WASM）** | 沙箱逃逸、资源耗尽 | wasmtime 沙箱；限制内存 64MB、CPU 时间 10ms、无文件与网络访问 |
| **依赖供应链** | 恶意包、CVE | `cargo-deny` + `cargo-audit` CI 门禁；锁定 `Cargo.lock`；SBOM 发布 |

### 9.3 防绕过设计（这是 WAF 的核心竞争力）

攻击者绕过 WAF 的手法有限且可枚举，我们逐条设防：

| 绕过手法 | 示例 | 防御 |
|---|---|---|
| **多重 URL 编码** | `%2527` → `'` | 最多 3 层递归解码，记录层数 flag |
| **Unicode 归一化** | 全角 `＇` → `'` | NFKC 归一化后再检测 |
| **大小写混写** | `SeLeCt` | 检测副本统一折叠 |
| **注释插入** | `UN/**/ION SEL/**/ECT` | 剥离 SQL 注释后再做词法分析 |
| **空白替换** | `UNION%09SELECT`、`UNION+SELECT` | 空白归一化 |
| **分块传输绕过** | chunked body 分段发送 payload | 流式检测保留跨块窗口（默认 8KB 重叠） |
| **Content-Type 欺骗** | 声明 `text/plain` 实为 JSON | 内容嗅探优先于声明；不一致时记 flag 并加严检测 |
| **参数污染** | `?id=1&id=1' OR 1=1` | 同名参数全部检测，不只取第一个 |
| **超长参数截断** | 在前 8KB 放正常内容，payload 放在后面 | 不截断检测，超限直接拒绝或分段全检 |
| **HTTP 请求走私** | `CL` 与 `TE` 冲突 | 严格拒绝歧义请求 |
| **NULL 字节** | `shell.php%00.jpg` | 剔除 NUL 后重新校验扩展名 |
| **UTF-8 超长编码** | `%c0%ae%c0%ae/` | 严格 UTF-8 校验，非法序列拒绝 |
| **IPv6 变形** | `::ffff:127.0.0.1` 绕过内网判定 | 地址族归一化后再判定 |
| **DNS 重绑定** | 首次解析公网 IP，二次解析内网 | SSRF 检测做二次解析比对（可配） |
| **分片慢速发送** | 每 10s 发一个字节 | 最小传输速率限制 + 头部/体读取超时 |

### 9.4 权限与沙箱

| 项 | 措施 |
|---|---|
| 运行用户 | 默认非 root；绑定 80/443 使用 `CAP_NET_BIND_SERVICE` 或 systemd socket 激活 |
| systemd 加固 | `NoNewPrivileges=yes`、`ProtectSystem=strict`、`ProtectHome=yes`、`PrivateTmp=yes`、`PrivateDevices=yes`、`RestrictAddressFamilies=AF_INET AF_INET6 AF_UNIX`、`SystemCallFilter=@system-service` |
| seccomp | 可选 profile，仅允许必要系统调用 |
| 文件系统 | 只读挂载（除数据目录）；配置与数据目录独立 |
| 能力 | 仅保留 `CAP_NET_BIND_SERVICE`，其余全部 drop |
| 内存保护 | 编译开启 `-C relro-level=full`、栈保护；`unsafe` 代码需审计注释并在 CI 中统计 |
| 崩溃隔离 | 请求处理任务 panic 被捕获，返回 500，进程不退出，记录 panic 位置 |

### 9.5 隐私设计

家庭场景下流量包含大量私人内容（照片、聊天、文档），隐私不是可选项。

| 原则 | 实现 |
|---|---|
| 默认不记录 body | 访问日志只记元数据；body 仅在触发安全事件时记录前 1KB 且脱敏 |
| 本地优先 | 无任何遥测上报；版本检查可关闭；不调用第三方 API（除用户显式配置的 ACME、DNS、告警通道） |
| 数据最小化 | GeoIP 只到国家/城市级，不存精确坐标 |
| 可删除 | 提供"清除所有日志"与"按 IP 删除记录"功能 |
| 加密传输 | 控制台强制 HTTPS（或仅本地回环）；告警 Webhook 支持自定义 CA |
| 敏感字段白名单 | 用户可配置额外需要脱敏的字段名（如 `id_card`、`passport`） |

## 10. 数据模型

### 10.1 存储选型

SQLite 单文件，WAL 模式，`synchronous=NORMAL`（兼顾性能与耐久性）。所有写入由单一写入任务串行化，避免锁竞争。

```
├── homewaf.db          # 主数据库
├── homewaf.db-wal      # WAL
├── certs/              # 证书与私钥（0600）
├── rules/              # 用户自定义规则（YAML）
├── geoip/              # GeoLite2 数据库
└── logs/               # 可选的滚动日志文件
```

### 10.2 表结构

```sql

    primary_domain TEXT NOT NULL,              -- 主域名
    alias_domains TEXT NOT NULL DEFAULT '[]',  -- JSON 数组，别名域名

    routes        TEXT NOT NULL DEFAULT '[]',  -- JSON: [{path, match_type, upstreams, rewrite, policy}]
```

## 12. 部署拓扑

### 12.1 拓扑 A：IPv6 直连（推荐给有公网 IPv6 的用户）

```
互联网 ──IPv6──► 家庭路由器（放行 443）──► HomeWAF (NAS/N100) ──► 内网服务
                                                    │
                                                    └─► 控制台（仅内网/回环）
```

要点：
- 仅暴露 443，80 端口仅用于 ACME HTTP-01（或改用 DNS-01 完全关闭 80）
- 防火墙只允许入站 443，出站不限制
- IPv6 地址会随前缀变化（PD 重新委派），需 DDNS 更新 AAAA 记录
- HomeWAF 需支持监听 `::` 并正确处理临时地址

### 12.2 拓扑 B：Cloudflare Tunnel / frp 回源

```
互联网 ──► Cloudflare ──tunnel──► cloudflared ──► HomeWAF (127.0.0.1:8080) ──► 内网服务
```

要点：
- HomeWAF 只监听回环，不暴露任何端口
- 必须信任 `cloudflared` 来源并解析 `CF-Connecting-IP`
- 此时真实客户端 IP 依赖头部，需严格校验来源（仅信任 127.0.0.1）

### 12.3 拓扑 C：纯内网（无公网暴露）

```
内网设备 ──► HomeWAF (192.168.1.10:443) ──► 内网服务
```

要点：
- 使用自签名 CA，内网设备安装信任
- 主要用于内网横向移动防护与访问审计
- 可开启 mTLS 做设备级认证

### 12.4 资源规划

| 场景 | 设备 | 内存 | 建议 |
|---|---|---|---|
| 轻度（1-3 应用，日请求 < 10 万） | 树莓派 4B 2GB | 2GB | 关闭语义引擎的响应方向检测，日志保留 14 天 |
| 中度（3-10 应用，日请求 < 100 万） | N100 16GB / 群晖 x86 | 4GB | 全功能开启，缓存 512MB |
| 重度（10+ 应用，日请求 > 100 万） | x86 4 核+ | 8GB | 开启 HTTP/3，缓存 2GB，日志外发 |

| 证书续期 | 模拟证书剩余 20 天 | 自动续期成功，零中断 |
| 规则热加载 | 修改规则文件 | 2 秒内生效，无请求失败 |
| 攻击拦截 | 用标准 payload 集测试 | 见 14.3 |
| 误报控制 | 30 天真实流量影子模式 | 误报率 ≤ 0.1% |
| 控制台 | 完整走一遍首次引导 | 非技术用户 10 分钟内完成 |
| 降级 | 用 `wrk` 打满队列 | 按 L1→L4 逐级降级，无 OOM，控制台可见 |

### 14.3 检测能力验收（关键）

自建**绕过回归语料库**，结构参考 OWASP CRS 的 go-ftw 测试框架：

```
tests/corpus/
├── sqli/
│   ├── positive/     # 必须检出（含编码变形、注释绕过、分块）
│   └── negative/     # 必须放行（O'Reilly、union 作为普通词、SQL 教程内容）
├── xss/
│   ├── positive/     # 含分段注入、上下文注入、编码绕过
│   └── negative/     # Markdown 富文本、代码块中的 HTML 示例
├── cmdi/
├── path-traversal/
├── ssrf/
└── ...
```

| 类别 | 正样本数（目标） | 检出率要求 | 负样本数 | 误报率要求 |
|---|---|---|---|---|
| SQL 注入 | 300 | ≥ 95% | 200 | ≤ 0.5% |
| XSS | 300 | ≥ 95% | 200 | ≤ 0.5% |
| 命令注入 | 150 | ≥ 93% | 100 | ≤ 0.5% |
| 路径遍历 | 150 | ≥ 97% | 100 | ≤ 0.2% |
| SSRF | 100 | ≥ 95% | 50 | ≤ 0.5% |

**负样本比正样本更重要**。一个 WAF 的失败通常不是"漏了什么"，而是"拦了不该拦的"。负样本必须包含真实家庭场景：相册上传、Markdown 笔记、代码仓库浏览、带引号的中文搜索、含 `<` `>` 的数学公式。

## 15. 风险与对策

| 编号 | 风险 | 影响 | 概率 | 对策 |
|---|---|---|---|---|
| R-1 | **语义检测器准确性不足**，误报高于预期 | 致命（用户直接卸载） | 高 | 先做影子模式；负样本优先；提供一键加白；v1.0 允许语义引擎默认"仅记录" |
| R-2 | **规则库建设成本被低估** | 高（检出率上不去） | 高 | 复用公开 payload 语料（PayloadsAllTheThings、OWASP）；社区贡献机制；不追求规则数量而追求质量 |
| R-3 | **性能达不到千兆线速** | 中 | 中 | M0 就做基准测试；预留降级开关；必要时用 `sendfile` 与零拷贝优化 |
| R-4 | **ARM 交叉编译与依赖问题**（aws-lc-rs 需要 CMake/汇编器） | 中 | 高 | 提供 `ring` 后端特性开关；CI 中覆盖 aarch64 构建 |
| R-5 | **ACME 在家庭网络的特殊性**（无 80 端口、CGNAT、IPv6 前缀变化） | 中 | 高 | DNS-01 作为一等方案；内置主流 DNS provider；文档明确说明 |
| R-6 | **单人/小团队维护不可持续** | 高 | 中 | 控制范围（不做企业特性）；模块化便于社区接手；完善文档 |
| R-7 | **用户不理解降级与 fail 策略**，误配置导致防护失效 | 中 | 中 | 默认值保守；控制台显式提示当前防护等级；配置校验时警告危险组合 |
| R-8 | **与现有 Nginx/Caddy 用户迁移摩擦** | 中 | 中 | 提供配置迁移工具（尽力而为）；支持"仅作为 WAF 前置"的串联模式 |
| R-9 | **SQLite 在高写入量下成为瓶颈** | 中 | 低 | 异步批量写入；日志采样；聚合表预计算；明确家用定位（不追求百万 QPS 日志） |
| R-10 | **法律与合规**（日志记录他人 IP 与请求内容） | 低 | 中 | 默认最小化记录；提供数据删除；文档提示用户遵守当地法规 |

## 16. 附录

### 16.1 术语表

| 术语 | 含义 |
|---|---|
| **vhost** | 虚拟主机，按域名区分的一组配置与上游 |
| **上游（Upstream）** | WAF 后面的真实服务 |
| **语义检测** | 通过词法/语法/上下文分析判断攻击意图，区别于正则匹配 |
| **异常评分** | 多条弱信号累加，达到阈值才阻断的判定模型 |
| **影子模式** | 规则只记录不阻断，用于评估误报 |
| **等待池** | 资源饱和时的有界请求队列，超时则快速失败 |
| **降级梯度** | 按压力逐级关闭高开销检测的分级策略 |
| **预算（Budget）** | 单个请求允许消耗的最大处理时间 |
| **偏执级别（Paranoia Level）** | 规则严格程度分级，级别越高检出越多误报越多 |
| **fail-open / fail-closed** | 检测失败时放行 / 拒绝 |

```yaml
  enabled: true
  email: "me@example.com"
  challenge: dns-01              # 家庭环境推荐，无需 80 端口
  provider: cloudflare
  credentials:
    api_token: "${CF_API_TOKEN}" # 从环境变量读取，不落盘
  renew_before_days: 30

# 真实客户端 IP：前面有 CDN / Tunnel / frp 时必配
real_ip:
  enabled: true
  preset: cloudflare             # 自动填充 trusted_proxies 与 header_priority
  log_both: true                 # 日志同时记录真实 IP 与直连 IP

limits:
  max_header_size: 32768
  max_header_count: 100
  max_body_size: 10485760        # 10MB
  max_url_length: 8192
  queue_capacity: 1024
  queue_timeout_ms: 200
  detect_budget_ms: 50
  request_timeout_s: 30

# 防护开关：17 类攻击，三态；档位批量预设
protection:
  preset: balanced               # lenient | balanced | strict | custom
  observe_mode:                  # 首次部署建议开启，观察 7 天
    enabled: false
    auto_disable_after: 7d
  sqli: block
  xss: block
  cmdi: block
  path_traversal: block
  xxe: block
  ssrf: block
  file_upload: monitor           # 相册应用建议只记录

  webshell: monitor
  sensitive_leak: monitor

# 访问控制

  private_network:
    action: allow                # 内网设备默认放行
  ipv6_prefix_match: 64          # IPv6 按 /64 聚合，应对地址漂移
  auto_ban:
    enabled: true
    trigger_score: 50
    durations: ["5m", "30m", "2h", "24h"]

ip_groups:
  - name: chaitin-shared
    source:
      url: "https://ip-35193.rivers.chaitin.cn/api/share/ip_group/cb8cc6282f7f4b58abf9f48b45a1f67b?format=cidr"
      interval: 6h
    action: challenge
    guards:
      min_prefix_v4: 8
      min_prefix_v6: 32
      max_delta_ratio: 0.5

rule_feeds:

    channel: stable

    update_window: "03:00-05:00"
    require_signature: true
    shadow_period: 6h

ratelimit:
  global_qps: 2000
  per_ip_qps: 100
  per_ip_conn: 64
  per_url_qps: 200

logging:
  level: info
  format: json
  retention_days: 30
  body_capture: on_block         # never | on_block | always
  redact:
    headers: ["authorization", "cookie", "x-api-key"]

      - { addr: 192.168.1.5, port: 5000 }
```

### 16.4 待决策项（需产品负责人确认）

| 编号 | 决策点 | 选项 | 建议 |
|---|---|---|---|
| D-1 | 开源许可证 | Apache-2.0 / AGPL-3.0 / MIT | **Apache-2.0**（便于商业采用，专利授权明确） |
| D-2 | 是否提供付费版 | 纯开源 / 开源+PRO | 建议纯开源，避免维护两套代码 |
| D-3 | 规则库是否独立仓库 | 内置 / 独立规则包 | **独立规则包**，可独立更新规则而不升级二进制 |
| D-4 | 是否支持 FastCGI 上游 | 支持 / 不支持 | v1.1 再支持，v1.0 用 HTTP 反代即可 |
| D-5 | 前端框架 | Svelte / Solid / Vue | **Svelte**（产物体积小，无虚拟 DOM 开销） |
| D-6 | 是否内置 GeoIP 库 | 内置 / 按需下载 | 按需下载（MaxMind 许可限制，且体积大） |
| D-7 | 默认检测模式 | 全量阻断 / 语义仅记录 | v1.0 语义引擎默认"记录"，跑满 30 天后引导用户开启阻断 |
| D-8 | 是否内置 CRS 转换产物 | 内置随二进制 / 首次启动引导下载 / 完全不提供 | **首次启动引导下载**（避免体积与许可证捆绑问题，且用户可主动选择） |
| D-9 | IP 组订阅的默认动作 | `block` / `challenge` / `log` | **`challenge`**（第三方列表必然有误标，家庭场景先验证再封更稳妥；用户可改） |
| D-10 | 规则转换器的实现深度 | 只做 CRS 实际用到的子集 / 完整 SecLang 规范 | **只做子集**（用 20% 成本覆盖 80% 价值，未实现的结构显式报错） |
| D-11 | 规则包是否单独发版 | 跟随主程序 / 独立版本号 | **独立版本号**（规则更新频率远高于引擎） |
| D-12 | 首版默认防护档位与观察模式 | `lenient` / `balanced` + 观察模式 | **已确认**：默认 `lenient`，首次部署引导开启观察模式 7 天；观察模式不影响 ACL/限流/认证 |
| D-13 | 内网地址默认策略 | `allow` / `normal` | **已确认**：默认 `allow`，但完全可配置（可关闭、可自定义网段列表）；公网部署时显示横向移动风险警告 |
| D-14 | 路径匹配是否支持正则 | 支持 / 仅前缀 | **已确认**：支持但默认关闭（`allow_regex: false`），需要时在应用级显式开启 |
| D-15 | 非幂等请求是否重试 | 默认不重试 / 默认重试 | **已确认**：默认不重试，避免重复上传与重复提交 |
| D-16 | 是否强制"一应用一域名" | 强制 / 推荐不强制 | **推荐不强制**：创建时引导并提示风险，但允许用路径聚合（部分应用不支持子路径部署） |
| D-17 | 真实 IP 还原的默认行为 | 关闭 / 开启但空可信段 | **默认关闭**：未配置 `trusted_proxies` 时解析头部等于允许伪造，必须显式开启 |
